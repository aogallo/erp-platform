# Design: Architecture Foundation & Spec Definition

## Technical Approach

This is a foundation change for a greenfield ERP. First, make the documentation and scaffolding enforce one architecture: DDD inside Hexagonal Architecture, organized by bounded-context feature folders. Then design the first executable slice around CRM customers and Sales invoices, with PostgreSQL/Flyway as source of truth, SQLAlchemy as mapper, FastAPI controllers as inbound adapters, and services/repositories behind explicit contracts.

## Architecture Decisions

| Decision | Choice | Alternatives considered | Rationale |
|---|---|---|---|
| Architecture style | Hexagonal + DDD, feature-based by bounded context | Vertical Slice, pure layer-first Clean Architecture | Matches `AGENTS.md` and dependency rule: domain remains framework-independent while feature folders keep ERP modules discoverable. |
| Context model | Canonical 8 contexts: IAM, CRM, Sales, Inventory, Purchasing, Accounting, Banking, HR | Current 6-context `AGENTS.md`; partial `docs/bounded-context.md`; Reports as context | Reconciles `erp.md`, PRD personas, and docs. Reports should consume read models, not own transactional rules yet. |
| Persistence | SQL migrations via Flyway; SQLAlchemy 2.x repositories; Unit of Work owns transactions | Alembic/autogenerated migrations; direct ORM access from controllers | Database is source of truth; manual SQL keeps schema changes explicit and reviewable. |
| FEL integration | Transactional Outbox + async worker + Infile adapter | Synchronous FEL during posting; hard-coded provider calls | Provider outages must not roll back local sale/accounting; adapter protects domain from Infile lock-in. |
| Auth | Self-hosted auth provider port; evaluate `fastapi-fullauth` first, AuthFort second; future OIDC/Auth0 adapter | Direct Auth0-only implementation | Preserves self-hosted roadmap while leaving a clean migration path to managed OIDC. |
| API routing | Prefix routes by bounded context, e.g. `/crm/customers`, `/sales/invoices` | Flat resource routes like `/customers` | Makes ownership explicit in a modular ERP where the same concept may appear in multiple contexts. |

## Data Flow

```text
POST /sales/invoices/{id}/post
  -> sales/controllers/invoices.py
  -> InvoicePostingService.post()
  -> UnitOfWork transaction
       -> invoice status: draft -> posted_pending_fel
       -> inventory stock deduction
       -> accounting journal entry
       -> outbox event: FelAuthorizationRequested
  -> commit
  -> worker polls outbox
  -> FelService(InfileAdapter).authorize()
       -> success: fel_authorized + UUID/document number
       -> transient failure: retry/backoff
       -> exhausted/manual retry: fel_failed -> enqueue retry
       -> credit flow: credited via credit note + reversal entries
```

## Interfaces / Contracts

```python
class UnitOfWork(Protocol):
    customers: CustomerRepository
    invoices: InvoiceRepository
    outbox: OutboxRepository
    async def commit(self) -> None: ...
    async def rollback(self) -> None: ...

class FelProvider(Protocol):
    async def authorize(self, invoice_id: int) -> FelResult: ...
    async def cancel_or_credit(self, invoice_id: int, reason: str) -> FelResult: ...

class AuthProvider(Protocol):
    async def authenticate(self, username: str, password: str) -> Principal: ...
    def require_permission(self, permission: str) -> None: ...
```

## Testing Strategy

| Layer | What to Test | Approach |
|---|---|---|
| Backend unit | Domain invariants, services, FEL retry decisions | `pytest` + `pytest-asyncio`, faked repositories/providers. |
| Backend integration | Repositories, Unit of Work, migrations, outbox polling | PostgreSQL from Docker Compose; Flyway before tests. |
| API contract | Customer and invoice endpoints/status errors | FastAPI test client/httpx async tests. |
| Frontend unit | Hooks, forms, schema validation | Vitest + React Testing Library. |
| CI | Formatting, lint, types, tests | Ruff, mypy/pyright, pytest, Vitest in GitHub Actions. |

## Migration / Rollout

No production migration required. This is additive scaffolding plus docs. Roll out in phases: P1 docs/ADRs, P2 customer/invoice specs already present, P3 scaffolding/tests/CI, P4 remaining module specs.
