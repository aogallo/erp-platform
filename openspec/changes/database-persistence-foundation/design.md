# Design: Database Persistence Foundation

## Technical Approach

Create the persistence foundation only: Flyway creates PostgreSQL extensions and bounded-context schemas, while SQLAlchemy provides shared async engine/session wiring that maps to committed SQL. No business tables, seed data, schema-per-tenant isolation, or enabled RLS policies are introduced in this slice.

The design follows the existing Hexagonal/DDD scaffold: services depend on repository and Unit of Work contracts, repositories adapt SQLAlchemy, and the Unit of Work owns transaction commit/rollback.

## Architecture Decisions

| Decision | Choice | Alternatives considered | Rationale |
|---|---|---|---|
| Migration ownership | Flyway SQL under `backend/migrations/sql/` with a checked-in `backend/flyway.conf` | Alembic/autogenerated migrations | Reviewable SQL is the database source of truth and prevents ORM-first schema drift. |
| Baseline scope | One baseline migration creates `pgcrypto` and schemas `iam`, `crm`, `sales`, `inventory`, `purchasing`, `accounting`, `banking`, `hr` | Create business tables now | Keeps first slice infrastructure-only and protects Accounting from inheriting premature table design. |
| ORM metadata | Shared `Base` and naming convention in `shared/db/sqlalchemy.py`; context models later live in `backend/src/{context}/repositories/models.py` | One global models package | Preserves bounded-context ownership while giving migrations/tests consistent metadata conventions. |
| Async session boundary | `shared/db/sqlalchemy.py` builds `AsyncEngine`, `async_sessionmaker`, and session dependency helpers; `shared/uow/sqlalchemy.py` implements transaction scope | Sessions opened in controllers/services | Existing policy forbids direct DB access and `session.commit()` outside UoW. |
| Naming | Add `contracts.py`, `repositories.py`, `sqlalchemy.py`, `settings.py`; keep `ports.py` only for current compatibility | Rename all existing ports immediately | New names are junior-friendly without causing unrelated churn in existing imports. |
| Tenant/RLS readiness | Tenant-scoped future tables require `tenant_id`; add session-hook placeholder for tenant/principal context but do not enable RLS | Enable RLS now | Requirements explicitly defer policies; hooks reduce later refactor risk. |

## Data Flow

```text
Controller -> Application Service -> UnitOfWork
                                   -> Repository adapter -> AsyncSession -> PostgreSQL
                                                ^                 |
Flyway SQL migrations --------------------------+-----------------+
```

Commit flow: services call repository methods, then `uow.commit()`. `SqlAlchemyUnitOfWork.__aexit__` rolls back uncommitted work on exceptions. Repositories never call `session.commit()`.

## Interfaces / Contracts

`UnitOfWork` remains the service-facing contract. New concrete implementation accepts an `async_sessionmaker[AsyncSession]`, constructs repository adapters from one session, commits once, and rolls back on failure.

Repository adapters accept `AsyncSession` and tenant/principal arguments explicitly. Future application table migrations must include: `id uuid primary key default gen_random_uuid()`, `created_at timestamptz not null`, `updated_at timestamptz not null`, `created_by uuid not null`, `updated_by uuid null`, and `tenant_id uuid not null` unless the table is explicitly global/system.

## Testing Strategy

| Layer | What to Test | Approach |
|---|---|---|
| Unit | Settings URL, metadata naming convention, UoW commit/rollback calls | pytest with fake async sessions/sessionmaker. |
| Integration | Flyway migration creates extension and schemas only | PostgreSQL test database; inspect `information_schema`/`pg_namespace`. |
| Static | No repository `session.commit()` outside UoW | Focused grep-style pytest or lint helper over `backend/src`. |
| E2E | Not applicable | No endpoint behavior in this slice. |

## Migration / Rollout

Run Flyway against development/test databases before adding any business table migrations. Existing environments have no persisted app schema, so rollback is dropping created schemas and Flyway history in development only. Production rollback must be forward SQL.
